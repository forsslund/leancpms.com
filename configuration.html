Configuration as code

Three YAML files describe an operator.

An operator's whole setup is three kinds of YAML file, kept in its own repository. Everything else, such as sessions, receipts and statements, the system derives from them.

Organization

Who is on the receipt, and how drivers pay.

Price list

Tariffs with dated price rows, plans and channels.

One site per station

Fuse groups with their budget, charge points with phase rotation, and outlets.

The organization

Who the operator is: the name, numbers and address on every receipt, and how drivers pay.

  • key is the stable name that the other documents use. Every object has one, so renaming something never breaks a reference.
  • payment_mode: direct means that drivers pay into the operator's own Stripe account, so the operator is the seller.
  • operator_id is needed once a site is published over OCPI; every EVSE id is derived from it.

The price list

One for the whole organization. A tariff is the price per kWh, a plan is the offer, and a channel says which plan a driver gets.

  • amounts: incl_vat says which side of the price is exact. The other side is calculated, so 4.70 incl. VAT stays 4.70 on the receipt.
  • Prices are dated rows. A price change is a new row with its date, and a row that has taken effect cannot be edited, so old receipts stay explainable.
  • Drop-in and roaming share one tariff, so they pay the same and a price change is one line.
  • Amounts are quoted strings, never floats. A float is not money.

A site

One file per station, with what the installer knows and nothing commercial: a site never names a price.

  • budget_amps is what the load balancer may use. It can be set below physical_fuse_amps, for example for a smaller grid subscription, but never above it.
  • phase_rotation is set per charge point. Boxes are often wired with the phases rotated so that single-phase cars spread over L1–L3, and the balancer needs to know which station phase each box draws from.
  • publish: true lists the site over OCPI, for example in Nobil. A published site must then give its address, coordinates and, for each public outlet, plug, phases and max_amps.
  • An outlet with public: false is not offered to drivers. The files contain no secrets: charge point keys are generated by the server.

How a change goes live

The same two commands work for all three kinds of file, as with infrastructure-as-code.

  • cpms manifest plan site.yaml shows what would change and any warnings, such as sessions that are running now. It checks the file against the organization's other documents: a budget above the fuse, a plan naming a missing tariff, or an edited price row is an error.
  • cpms manifest apply applies exactly what was planned, with a message saying why. If the document changed on the server since the plan, it refuses, and you plan again.
  • Nothing is removed unless you pass --prune.
  • Every applied version is kept with its message and author: cpms manifest history lists them.

The command line is on PyPI as leancpms-cli:

uv tool install leancpms-cli    # or: pipx install leancpms-cli
cpms login --url https://cpms.example.com

cpms login opens your browser, where you log in to the portal and approve the key.

There is a JSON Schema for the files, so editors can validate and autocomplete them as you type. It comes with the command line: cpms manifest schema. cpms manifest validate checks a file offline.

Your files, your repository

It works the same whether you self-host or use LeanCPMS Cloud. Keep the files in your own git repository, review changes as pull requests, or let an AI agent propose them.
