The driver flow (cpms/driver/)¶

Drop-in charging for a driver with no account, no app and no login (PRD §2, architecture §3): scan the static QR code, see the price, pay by card, plug in, watch, stop, get a receipt. Goal: QR → charging in under a minute on a phone.

Pages¶

URL What
/ only on a host in an organization's driver_hosts: its published sites, each with its public outlets, their live status (the QR page's badge) and a link to /c/<public_id>. The ad hoc price incl. VAT once at the top. HTMX polls every 30 s. A 404 on any other host.
/c/<public_id> the QR code (Outlet.public_id: declared in the site document, or generated on first apply; stable across applies). Station, charge point, outlet, live status, the ad hoc price incl. VAT and the amount reserved, shown before anything starts (AFIR). E-mail for the receipt, accept, optionally "Start later" at a time of day, continue to payment.
provider's page Stripe Checkout (or /pay/fake/<ref> in development) reserves the amount.
/s/<token> the live page. Waiting for the payment → "plug in the cable" (with the time left) → "checking that the cable is locked" → kW, kWh, cost so far incl. VAT, Stop (or, scheduled: "charging starts at 23:00", start now, cancel) → finishing → done, with the receipt. A failed start is said here at once. HTMX polls every 3 s.
/s/<token>/receipt the receipt (seller = the organization). Also e-mailed.

<token> is a capability: 24 random bytes, the only key to that one charge. A reloaded page, a locked phone or a second device finds the charge again with the link, and the receipt mail links back to it. The outlet page also remembers the browser's own active charge for a day (a signed cookie per outlet) and offers "show my charge".

Swedish first (LANGUAGE_CODE = "sv"), English available from the footer. Strings are English in the source; the catalog is cpms/locale/sv/LC_MESSAGES/django.po, maintained with uv run python scripts/messages.py (no GNU gettext needed; --check lists anything untranslated).

What happens, step by step¶

Views are thin; every change is an action in services.py, journaled in the actions journal (never with the e-mail address, the tag or the token). Everything after the payment page is done by the worker (uv run manage.py worker), so it happens whether or not the driver's phone is still on the page.

  1. Begin (driver_begin). The outlet must be public, priced (the price list's ad hoc channel, flat tariffs only for now) and free: cpms's own read models first, then a live GET /chargers/{id} to ocpp-rest (responsive? this connector free?) right before any money is reserved. A DropIn row is created with the price shown, and the provider's checkout is opened for the plan's preauth_amount.
  2. Payment confirmed (driver_confirm_payment). Triggered by the provider's webhook (stored in the inbox, processed by the worker), by the driver's return (the worker asks the provider a couple of seconds later), or by a once-a-minute check. Each asks the provider directly; the driver's browser is never trusted. The authorization becomes a ledger Payment.
  3. Start (driver_start). A one-time id_tag (DRP + 17 random characters, 20 in total: the OCPP limit) is pushed with PUT /authorizations/{id_tag} scoped to this one box and expiring after the plug-in window, then POST …/connectors/{n}/start. The Aura then waits for the cable.
  4. Track (worker, every second). The session is found as consumer.Session with this box and this id_tag (a session the consumer attributes to another organization is never taken). If the gateway missed the session_start and the session was learned without a tag, the one learned session on this outlet since our start is taken, and only if there is exactly one.
    • No session within DRIVER_PLUG_TIMEOUT_S (default 180 s; it must be longer than ocpp-rest's REMOTE_START_GRACE_S, 120 s): the tag is revoked first, then the reservation is released.
    • The cost reaches the reservation: the worker sends one RemoteStop.
    • The session ends, by our Stop or because the driver unplugged: the drop-in is ended.
    • A session that appears after we gave up (the box started anyway) is stopped: the unpaid-session guard.
  5. Settle (settle_payment, in cpms/ledger/). After DRIVER_SETTLE_DELAY_S (30 s) from a definitive session_end, or DRIVER_SETTLE_DELAY_INFERRED_S (300 s) from an inferred one (a definitive end with the box's own meter value may follow), the session's amount_incl_vat is captured, capped at the authorization; 0 kWh (or anything below the provider's minimum) cancels instead. If the consumer could not price the session, the price shown to the driver is used.
  6. Receipt mail and tag revocation. At least once; a crash between sending and recording resends the same receipt (same number).

Scheduled start (PRD §6, slice 3a)¶

"Start later" on the outlet page takes a time of day in the organization's time zone, the next time the clock shows it; services.begin takes any start_at (the driver API passes it on). The session starts at once, exactly as without it: the RemoteStart carries a limit of 0 A, which ocpp-rest puts into the first TxProfile, so the cable locks while the driver is at the car and no energy flows. The balancer is the scheduler (architecture §9): it reads start_at from GET /api/v1/balancer/sessions, keeps the session at 0 A until then and gives it its share from the next cycle after (cpms/balancer/README.md). The drop-in is scheduled from the session's start until start_at, then charging.

  • Start now sets start_at to now; cancel stops the session (0 Wh, the reservation is released, no failed-start notice: she cancelled).
  • Only where the fuse group is balanced (balancing: true): without a balancer nothing would hold the car (scheduling_not_available).
  • At most the provider's authorization window (Stripe: 7 days for an online card payment) less DRIVER_SCHEDULE_MARGIN_S (2 days) ahead (start_too_late): an authorization that expires before the capture loses the money (architecture §3.1). The page offers only the next 24 h.
  • If no car is plugged in within the plug-in window, or the driver starts now before plugging in, the 0 A is taken off the connector so the next car does not start paused.

A failed start is never silent (PRD §6)¶

The consumer judges each session (Session.failed_start, cpms/consumer/README.md): it ended within a minute with 0 Wh, ended without energy after it was allowed current, delivered nothing for five minutes after it was allowed current (for a scheduled start: after start_at), or its outlet went Faulted under it. For every drop-in, scheduled or not:

  • the live page says so at once (it reads the session itself, every 3 s): "The charge did not start … unplug the cable, push it firmly in, and start again", or for a running session with no energy, what to check, with Stop;
  • the worker records it once (driver_failed_start, journaled) and e-mails the receipt address (driver_send_failed_start_mail, at least once, like the receipt);
  • the session settles as usual: 0 Wh cancels the reservation, no receipt.

A charge a fault stops after it has delivered (Jonas, 2026-11-06; the consumer's Session.interrupted_at) gets the same treatment, but is not a failed start: "The charge has stopped" on the page at once, with the re-plug advice and Stop, and one e-mail (driver_interrupted, driver_send_interrupted_mail). Nothing is stopped automatically. If the outlet leaves Faulted and the charge resumes, the page shows charging again; a second fault shows on the page but sends no second e-mail. The receipt follows as usual for the energy delivered.

Not reported to the driver: a session she stopped herself. Energy delivered later clears the session's state; the drop-in keeps the record that she was told. Right after the box starts a session the page shows "checking that the cable is locked" for DRIVER_LOCK_CHECK_S (15 s, architecture §3.1). Both numbers are provisional until they are measured on real hardware.

States: paying → authorized → starting → charging → ended (or starting → scheduled → charging, or scheduled → ended when cancelled), or abandoned (left the payment page, or DRIVER_CHECKOUT_TIMEOUT_S passed: the checkout is expired at the provider so it cannot be paid later), failed (declined, or the start failed), timed_out (no car, or the driver pressed Cancel). Every non-ended end releases any reservation; a payment that arrives after the drop-in gave up is recorded and released.

A second driver cannot pay for an outlet that is starting or charging; a driver on the payment page holds the outlet for three minutes.

The driver API (/api/driver/v1/, architecture §3.1)¶

The contract for an organization's own driver front end (api.py): a django-ninja API of its own, with its own OpenAPI document (/api/driver/v1/openapi.json) and docs page (/api/driver/v1/docs), separate from the operator API. v1 changes only additively; state and payment.kind say they may grow. The served pages stay the reference client: both call the same actions, and a test runs one drop-in through each and compares the journal and the ledger.

Endpoint Credential What
GET /outlets/{public_id} none, any origin the outlet by its QR id: site, charge point, live status, can_start, the ad hoc price incl. and excl. VAT (exact names the side the tariff states), the amount reserved, and scheduling (available here, how far ahead)
GET /organizations/{key}/sites none, any origin the published sites and their public outlets, as the home page
POST /outlets/{public_id}/start none {email, accept, language?, return_url?, start_at?} → 201 {token, session}; the session is payment_required with payment.checkout_url. accept must be true: the driver accepted the price and the reservation shown, as the served page's checkbox asks (422 price_not_accepted otherwise)
GET /sessions/{id} session token the session, live: state (payment_required, starting, scheduled, charging, finishing, ended, failed_start, cancelled, failed), held, checking_cable, failed_start, interrupted, energy, power, cost, payment
POST /sessions/{id}/cancel-payment session token the driver left the payment page
POST /sessions/{id}/cancel session token give up before the car is in; a scheduled charge: stop it
POST /sessions/{id}/start-now session token a scheduled charge: do not wait
POST /sessions/{id}/stop session token stop charging
GET /sessions/{id}/receipt session token the receipt, once captured (404 before)
  • The session token is the capability /s/<token> is: 24 random bytes, returned once by start, sent as Authorization: Bearer. {id} is the session's public id (DropIn.ref); a token reaches its own session only, and another id is a 404.
  • Refusals are errors with the codes the served pages translate: occupied, starting, offline, out_of_order, not_public, no_price, payments_not_set_up, payment_provider_unavailable, scheduling_not_available, start_too_late, return_url_not_allowed, invalid_email, invalid_language, too_many_requests, price_not_accepted (422; the served page shows the unticked box's message for it).
  • Allowed origins (cors.py). The public endpoints answer any origin. Start and the session endpoints answer a browser only from the organization's driver_origins (organization document; https, or http://localhost for development) and the hosts the instance serves the driver flow on itself (its driver_hosts, PUBLIC_BASE_URL, the named ALLOWED_HOSTS). The same list binds return_url for every caller: payment never returns to a page that is not the operator's. Payment returns to return_url with session=<id>&payment=done or payment=cancelled added; without it, to the served live page.
  • Rate limit. Start is limited per client address (an IPv6 /64), START_LIMIT (10 per 10 minutes), in front of the action, shared with the served page (cpms.core.limits: per process, enough to blunt abuse).
  • Not yet: the driver token, login and the account endpoints come with driver accounts (PRD §7, slice 5a); the subscription endpoints with the subscriber step.

Theme¶

No project or customer branding is built in (architecture §14). The organization's name comes from the organization document; an optional theme block there sets an accent colour and a logo:

organization:
  key: demo
  name: Demo Laddning AB
  theme: {primary: "#0b7a3e", logo_url: "https://example.com/logo.svg"}

Both are validated by the manifest schema (hex colour, https URL), so nothing reaches the page's CSS unchecked. The return URL from the payment page uses the host the driver came in on, so an organization's own domain (charge.example.se pointed at the instance) stays its own through payment.

Design system¶

Server-rendered Django templates + HTMX + Tailwind with daisyUI (PRD §5).

  • Partials. A page and its HTMX fragment are the same template: Django 6's template partials ({% partialdef panel inline %} and render(…, "driver/live.html#panel")). Small components are includes in templates/driver/components/ (price, stat, receipt, outlet header).
  • Tailwind without Node at runtime. scripts/build-css.sh downloads Tailwind's standalone CLI (a single binary with Tailwind built in, published by Tailwind Labs for exactly this) and daisyUI's two plugin files at pinned versions with checked SHA-256s into .tools/ (gitignored), and builds cpms/assets/app.css into cpms/static/cpms/app.css, which is committed. The server never builds CSS; it serves the committed file after collectstatic. Rebuild and commit after changing classes in a template. The same approach is the default in Phoenix (the tailwind hex package), in Rails (tailwindcss-rails) and in Django's django-tailwind-cli; daisyUI documents its use with the standalone CLI. Not thought through yet: nothing checks in CI that the committed CSS is up to date with the templates.
  • htmx 2.0.4 is vendored as cpms/static/vendor/htmx-2.0.4.min.js.
  • Mobile first: one column, max-w-md, tap targets of at least 48 px.

Not built yet¶

Spot-priced drop-in (needs the current spot price on the page), an EVSE id on the page and receipt (architecture §14, comes with the OCPI slice), driver accounts and the driver token (slice 5a), per-organization sender domains for mail (today: DEFAULT_FROM_EMAIL with the organization's name, and its e-mail as Reply-To).
