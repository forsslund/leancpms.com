Users and access¶

How people and machines get into LeanCPMS, what each of them may do, and how an organization manages that itself. It is written for two readers: someone who wants to understand the model without reading code, and an organization's administrator who is about to manage their organization from the command line.

The worked example is LeanCPMS Cloud, the hosted instance run by Forsslund Systems AB. A self-hosted instance works the same way under its own host names; the differences are at the end. The examples use a made-up organization acme and addresses at example.com.

This describes the code as it is (leancpms-cli 0.1.4). The design and its reasons are in docs/architecture.md §3 and §11.

1. Concepts¶

People¶

A person is one e-mail address. There are no passwords and no user names. To log in to the portal you type your address, LeanCPMS e-mails you a short one-time code, and you type the code. Everything a person does, in the portal and on the command line, goes back to that one identity.

Nobody signs up. An address can log in only after someone has made it a member (below). An address that is not a member gets no code at all, not even an error message, so that the login page does not reveal who has an account.

The operator and organizations¶

An instance holds several organizations. An organization is a company that owns charging stations: its sites, charge points, price list, sessions, receipts and monthly settlements belong to it, and it cannot see anyone else's.

The operator is whoever runs the instance. On LeanCPMS Cloud that is Forsslund Systems AB. The operator is not an organization; it stands above all of them and sees every organization.

Memberships and roles¶

A membership connects a person to one organization, or to the operator. A person can have several: member of acme and of globex, say. Each membership has a role:

Role In the portal On the command line
read (the default) sees everything about the organization gets keys that may only look
write the same: the portal only reads, whatever the role gets keys that may also act: apply manifests, manage members and keys, stop sessions

So the role does not change what you see; it caps what the keys you get with cpms login may do (see Keys).

Each membership records who added it. Removing a person does not remove the members they added: when someone leaves, look at cpms members list and decide about the people they brought in.

The operator membership is the admin¶

A membership without an organization is an operator membership. It is the instance's "superuser":

  • In the portal it shows every organization.
  • It is the only way into the Django admin pages at /admin/, which are a read-only view of every table (cpms/portal/admin_site.py).
  • With cpms login it can get an operator key, which reaches every organization and the operator-only commands (opening the gateway to unknown charge points, the organization document, the balancer).

Django's own is_staff and is_superuser flags decide nothing about access: nobody gets into /admin/ or sees an extra organization because of them, and they are never needed. Their one effect is protective: an organization's key cannot add, change or remove an account that has one of those flags, and losing a membership never switches such an account off (cpms/actions/members.py). Operator memberships are given by the operator only; an organization can never create one.

API keys¶

Everything that is not a person in a browser talks to the instance's JSON API with an API key, sent as Authorization: Bearer <key>. The command line cpms is one such client.

A key looks like lcp_3f9a1c2e_<43 more characters>. The part after lcp_, here 3f9a1c2e, is its prefix: it is not secret, it names the key in lists and logs, and it is what you revoke. The rest is the secret. The instance stores only a hash of the whole key, so a key is shown exactly once, when it is made, and can never be shown again. Lose it and you make a new one.

Every key has three properties:

  • Who it is for. An organization key reaches one organization. An operator key reaches every organization and the operator-only commands.
  • Its scope. A read key may only look (HTTP GET). A write key may also act. A read key may do one thing besides looking: revoke itself (cpms logout).
  • Whose it is. A personal key belongs to a person: cpms login gets it after the person approved it in the portal, and it is named after the computer, such as cpms on anna-laptop. A machine key belongs to no person: it is made with cpms keys issue for a script, a CI pipeline, a dashboard or an agent, and it records which key issued it.

The rules that follow from that:

  • A role caps personal keys. A read member gets only read keys from cpms login. A write member may choose either.
  • A key never makes a wider key. An organization's write key may issue keys for its own organization, read or write; never an operator key, never a key for another organization. A read key issues nothing, and may not list keys or members either, since lists of keys and members are part of managing them.
  • Removing a member revokes their keys, and every key made from them. When a person loses a membership, their personal keys for it stop working, and so does every machine key issued with one of those keys, and every key issued with those, however far down. A personal key the person had already revoked (with cpms logout, say) still counts: the keys made from it go too.
  • Lowering a role does the same for write. Lowered from write to read, a member's personal write keys are revoked, together with every key issued from them, including read keys issued from them.
  • A switched-off account's keys stop working. A person whose last membership is removed is switched off: they can no longer log in, their portal login ends, and any personal key of theirs still left is refused.
  • Revoking one key revokes only that key. cpms keys revoke and cpms logout do not cascade: machine keys issued with the revoked key keep working. They still die with their maker's membership, as above.

The consequence to remember: a machine key lives only as long as the membership of the person whose key issued it. That is deliberate, so that nobody leaves behind working keys when they leave. A key for an integration that must keep working when people come and go is issued by the operator, from a key with no person in its chain (see Common tasks).

Who owns or issued a key, and who added a member, is shown as an e-mail address only to those who may see that person in the members list: the operator, and the organization the person is a member of now. Others see "operator" or "former member".

What each kind of key may do¶

organization read key organization write key operator key
Live state, sessions, events, monthly settlements own organization own organization every organization
Export manifests, history, diff own organization own organization every organization
Plan and apply the price list and site documents no own organization every organization
Plan and apply the organization document no no yes
Stop or close a session, rekey a charge point no own organization every organization
OCPI connections look own organization every organization
List, add, remove members, change roles no own organization's members (never an operator member) everyone
List, issue, revoke keys no own organization's keys every key
The gateway's admission window for unknown charge points (cpms admission) no no yes (opening it needs write)
Revoke itself (cpms logout), cpms whoami yes yes yes

An operator key also has a scope: an operator read key looks at everything and changes nothing.

Other credentials¶

These are not for people and not for the API, but they exist and it helps to know who handles them.

  • OCPI tokens. A roaming partner (an eMSP, or a registry such as Nobil) talks to the instance over OCPI with tokens of its own, one connection per organization and partner. cpms ocpi connect acme --name partner makes the connection and prints Token A once, to send to the partner; the partner registers, and the tokens are exchanged automatically. cpms ocpi disconnect ends it. An organization's write key may do this for its own organization; on LeanCPMS Cloud the operator usually does.
  • Charge point passwords. Each charge point declared with auth: basic in its site document has its own password for its OCPP connection. The gateway sets it on the box over OCPP; it is in no file and nobody sees it. cpms chargepoints rekey <key> replaces it.
  • Driver session tokens. A driver who pays by card at the QR code gets a link to their own session (/s/<token>). The token is the only key to that one charge. Drivers hold these; nobody at the organization needs them.
  • Instance secrets. The balancer's own operator key, the key between LeanCPMS and its gateway, the payment provider's keys: these live on the server and are the operator's (deploy/README.md).

The actions journal¶

Every change (adding a member, issuing or revoking a key, applying a manifest, approving a cpms login) writes a row to the actions journal: who, when, what, and the result. It never stores a secret or an e-mail address; it stores the key's prefix. That is what answers "who did this, and when" afterwards.

2. On LeanCPMS Cloud¶

Host names¶

Address For whom What
https://portal.leancpms.com people the portal, the admin pages, and the page where you approve cpms login
https://api.leancpms.com machines the JSON API (docs at /api/v1/docs), the command line, OCPI
wss://ocpp.leancpms.com charge points the OCPP connection
the organization's own domain, e.g. charge.example.com, or acme.leancpms.com drivers the station list, the QR pages and the driver API
https://leancpms.com everyone the website, hosted apart from the instance

The portal and the admin pages answer only on portal.leancpms.com. Asked for on any other of the names, they redirect there, so a driver's domain never shows a login page. The API answers on api.leancpms.com; use that address with the command line.

How someone becomes a member¶

There is no page for it. Members are added from the command line, or through the API it uses:

  1. The operator adds the organization's first administrator, with an operator key:

    cpms members add anna@example.com --org acme --role write

  2. That administrator adds colleagues, with their own personal write key:

    cpms members add ben@example.com --org acme              # read (the default)
cpms members add carla@example.com --org acme --role write

Nothing is e-mailed when a member is added. Tell the person yourself to go to https://portal.leancpms.com and log in with that address.

An organization can manage only its own members. It cannot see or change an operator member, and it learns nothing about a person's memberships elsewhere.

Logging in to the portal¶

  1. Open https://portal.leancpms.com.
  2. Type your e-mail address. A code is e-mailed to you; type it on the next page. If no mail comes, the address is not a member (or has a typo): ask whoever was to add you.
  3. With one organization you land on its overview; with several, on a list of them.

A login lasts 90 days on that browser, or until you log out (top right) or your last membership is removed. The portal shows, for each organization: an overview with live state, sessions, receipts and the monthly settlements. It only reads. Its texts follow the browser's language (Swedish or English).

Because the code goes to your e-mail, your mailbox is your password: whoever can read your mail can log in as you.

The admin pages¶

An operator member also sees an Admin button in the portal, which leads to https://portal.leancpms.com/admin/. Opened directly without a login, it sends you through the same code login first. Organization members get "403 Forbidden" there, whatever their role. The admin pages are read-only: changes are made with cpms and an operator key, never in the admin.

3. The command line¶

cpms is a small program you install on your own computer. It talks to api.leancpms.com with your personal key. The examples assume a Unix shell (Linux or macOS).

Install¶

leancpms-cli is published on PyPI, so it installs without access to the source repository. The recommended way is with uv, which also fetches Python 3.14 if your computer lacks it:

curl -LsSf https://astral.sh/uv/install.sh | sh     # if you do not have uv yet
uv tool install leancpms-cli
cpms --help
  • Upgrade: uv tool upgrade leancpms-cli. To pin a version: uv tool install leancpms-cli==0.1.4.
  • pipx works too, if Python 3.14 is already installed: pipx install leancpms-cli.
  • Other routes, for those with access to the repository while it is private: the wheel on the GitHub release (gh release download cli-v0.1.4 --repo forsslund/leancpms --pattern '*.whl', then uv tool install ./leancpms_cli-0.1.4-py3-none-any.whl), or straight from git (uv tool install "git+https://github.com/forsslund/leancpms#subdirectory=cli"). Both fail without repository access; PyPI does not.
  • Do not install it where the LeanCPMS server is installed: the server already contains cpms.

Log in: cpms login¶

cpms login --url https://api.leancpms.com

This is the same "device login" as gh auth login:

  1. cpms asks the instance for a login and prints a page address and a code, such as KTRW-MZPB. It opens the page in your browser if it can (--no-browser only prints it, for a server over ssh).
  2. In the browser you land on portal.leancpms.com/portal/cli/. Log in with your e-mail code if you are not already logged in.
  3. The page shows the code, what asks for the key (cpms on <your computer's name>), when, and from which internet address. Check that the code is the one in your terminal. Approve only a login you just started yourself: whoever started it gets a key in your name.
  4. Choose the organization and what the key may do. A write member sees "may look and act (write)" and "may only look (read)"; a read member only the latter. --scope read on the command line preselects read.
  5. Approve. The terminal continues by itself and saves the key.

The code is valid for ten minutes and works once. Ten wrong codes in an hour lock the approval page for you for an hour.

The key is saved in the config file, ~/.config/cpms/config.toml, readable only by you:

[default]
url = "https://api.leancpms.com"
api_key = "lcp_3f9a1c2e_…"

Logging in again replaces the key in that profile; the old one keeps working until you revoke it (cpms keys revoke).

Profiles¶

Each [name] in the config file is a profile: an address and a key. cpms login writes [default] unless you name another, and leaves the other profiles as they are. Pick a profile with --profile or the environment variable CPMS_PROFILE:

cpms login --url https://api.leancpms.com --profile acme-read --scope read
cpms --profile acme-read sessions --since 2026-11-01
CPMS_PROFILE=acme-read cpms sessions

Use one profile per organization if you are a member of several, since a personal key is for one organization.

Instead of a profile, a script can set CPMS_URL and CPMS_API_KEY in its environment. Without --profile, the environment wins over [default]. CPMS_CONFIG points at another config file. A command that finds no key exits with code 2 and says what to set.

cpms whoami and cpms logout¶

$ cpms whoami
anna@example.com: write key 3f9a1c2e (cpms on anna-laptop) for organization acme

$ cpms logout
revoked key 3f9a1c2e
removed profile [default] from /home/anna/.config/cpms/config.toml

whoami says which key is in use: whose, for which organization, read or write. logout revokes the key in use on the server, then removes the profile. It revokes whatever key the profile holds, so never run it on a profile that holds an integration's machine key. A key from CPMS_API_KEY is revoked but stays in your environment; unset it.

Several computers¶

Run cpms login on each computer. Each gets its own personal key, named after the computer, so you can revoke one without touching the others. Do not copy the config file between computers: the same key in two places cannot be revoked in one of them only.

When a computer is lost or stolen¶

The lost computer holds your personal key in ~/.config/cpms/config.toml, and perhaps a portal login in its browser.

  1. Secure your e-mail first. Whoever reads your mail can log in as you.

  2. Revoke the key. From another computer, log in (cpms login), then find the key named after the lost computer and revoke it:

    cpms keys list
# prefix    organization  scope  name                  personal (owner)  issued by         created ...
# 3f9a1c2e  acme          write  cpms on anna-laptop   anna@example.com  anna@example.com  ...
cpms keys revoke 3f9a1c2e

    Listing and revoking keys needs a write key. A read member asks a colleague with write, or the operator, to do it.

  3. Machine keys whose secrets were on that computer (in another profile, a script, a .env file) must be revoked too: revoking your personal key does not revoke keys issued from it.

  4. The portal login in its browser lasts up to 90 days and cannot be ended from elsewhere by you. The operator can end it by removing your memberships, which switches the account off, and adding you again. That also revokes your personal keys and every key issued from them, so decide first which machine keys must be issued anew. The portal only reads, but it shows sessions and receipts, which hold drivers' personal data.

Everyday commands¶

Every command takes --json for machine-readable output and --profile. cpms <command> --help lists the rest.

Who is a member, and with which role

cpms members list
cpms members add ben@example.com --org acme                 # read
cpms members add carla@example.com --org acme --role write
cpms members set-role ben@example.com --org acme --role write
cpms members remove ben@example.com --org acme

--org acme is needed even though your key is already for acme. members list shows each member's role, whether the account is active, when they were added and by whom.

Keys

cpms keys list                                   # every key of the organization, revoked ones too
cpms keys issue --name dashboard --scope read    # prints the secret once
cpms keys revoke 7b2d90aa

keys issue makes a key for your own organization; the default scope is write, so say --scope read when looking is enough. The secret is printed on its own line on standard output, so it can go straight into a secret store: cpms keys issue --name ci --scope read > ci-key.txt.

Declared state: organization, price list, sites

These are YAML documents, kept best in a git repository of your own (cli/README.md, "A repository of manifests"):

cpms manifest export acme > all.yaml                  # every document
cpms manifest export acme --site main-street > sites/main-street.yaml
cpms manifest validate sites/main-street.yaml         # offline, needs no key
cpms manifest plan sites/main-street.yaml             # what would change; needs a write key
cpms manifest apply sites/main-street.yaml -m "Fused up to 50 A"
cpms manifest history acme --site main-street
cpms manifest diff acme --site main-street v3

apply shows the plan and asks before it applies; -m (the reason, stored with the version) is required. Removing anything needs --prune. An organization's key applies the price list and site documents; the organization document is changed by the operator.

Live state, sessions, the monthly settlements

cpms                                          # live state: sites, outlets, current per phase
cpms sessions --since 2026-11-01 --status ended
cpms sessions --since 2026-11-01 --csv > november.csv
cpms session SIM-0001/42                      # one session: <charge point>/<transaction>
cpms session SIM-0001/42 stop                 # acts at once, no confirmation
cpms report settlements --month 2026-10

Scripts, CI and agents¶

A script or an agent uses a machine key in CPMS_URL and CPMS_API_KEY, never on the command line, where it ends up in shell history and process lists. Exit codes: 0 ok, 1 the server said no or could not be reached, 2 usage or configuration. manifest apply never asks without a terminal: it prints the plan and exits 2 unless given --yes. More in cli/README.md, "For agents".

4. Common tasks¶

Add a colleague¶

cpms members add ben@example.com --org acme      # or --role write to let them act

Then tell Ben to log in at https://portal.leancpms.com with that address, and, if he will use the command line, to install cpms and run cpms login --url https://api.leancpms.com.

Give or lower a role¶

cpms members set-role ben@example.com --org acme --role write
cpms members set-role ben@example.com --org acme --role read

Raised to write, Ben runs cpms login again to get a write key; his read key stays as it was. Lowered to read, his write keys are revoked at once, and so is every key issued from them; the output lists their prefixes. Look at cpms keys list first if he made keys for integrations.

Remove someone¶

cpms keys list                                   # first: which keys did they issue?
cpms members list                                # and whom did they add?
cpms members remove ben@example.com --org acme

This revokes Ben's personal keys for acme and every key issued from them, and lists the revoked prefixes. If it was his last membership his account is switched off and his portal login ends. The members he added stay: decide about them separately. Any integration running on a key Ben issued stops now; give it a new key first (next task).

A key for an integration that must outlive a person¶

A dashboard, an accounting export, an agent: anything that should keep working when the person who set it up leaves.

A key issued with your personal key dies with your membership. Ask the operator instead, saying what it is for and whether it needs write.

The operator must issue it from a key with no person anywhere in its chain: a key made on the server with manage.py issue_key, or a key issued from such a key. A key the operator issues with their own personal operator key would in turn die with their operator membership. With such a person-free operator key in its environment, the operator runs:

cpms keys issue --org acme --name accounting-export --scope read

It appears in your cpms keys list with "operator" as its issuer (or nothing, if it was made directly on the server). Your organization can still revoke it.

If the integration may die with you (a script of your own, a test), issue it yourself:

cpms keys issue --name my-script --scope read

Revoke a key¶

cpms keys list               # find its prefix
cpms keys revoke 7b2d90aa

It stops working at once. Only that key is revoked: keys issued from it keep working until revoked themselves, or until their maker's membership ends. An organization's write key may revoke any key of the organization: a colleague's personal key, a machine key, or one the operator issued for it. To revoke the key you are using yourself, run cpms logout.

5. Running your own instance¶

The model is the same; only the names and the first step differ.

  • The host names come from the server's settings: PORTAL_URL (where the portal and the admin answer; other hosts redirect there), PUBLIC_BASE_URL (the drivers' host in receipt links), each organization's driver_hosts in its organization document, and DJANGO_ALLOWED_HOSTS for every name. One name for everything works too: leave PORTAL_URL empty and every host serves the portal.

  • The first operator. Nobody can log in until someone is a member, so the first key comes from the server:

    sudo leancpms-manage issue_key --operator --name bootstrap   # prints an operator key once
CPMS_URL=https://cpms.example.com CPMS_API_KEY=lcp_… \
  cpms members add you@example.com --operator --role write
cpms login --url https://cpms.example.com                    # choose "Operator: every organization"

    Revoke the bootstrap key once you have your personal one, or keep it as the person-free key that issues integration keys.

  • Login codes are e-mailed through the SMTP server in the settings; in development without one, the mail is printed in the server's log (dev/README.md).

In the code: people and roles cpms/portal/models.py, cpms/portal/access.py; the admin cpms/portal/admin_site.py; member actions cpms/actions/members.py; key actions cpms/actions/keys.py and cpms/core/keys.py; cpms login cpms/actions/login.py, cpms/api/login.py, cpms/portal/cli.py, cpms/cli/login.py; scopes on every request cpms/api/auth.py.
